# Speed: where Keen 4's time goes (2026-10-12)

The user reported that sound and music slow down on Android (Galaxy S26 Ultra) and that the map tears there. Every one of those sound problems (static, then stutter, then slow motion) came from the machine falling behind real time on the phone. The sound fixes only changed how the shortfall is heard. The real fix is speed.

## Measurement (PC, Keen 4 level 1, walking, native view on, unthrottled, 30 s)

The run used temporary timers around RF_Refresh's parts in gal_rf.gd, since removed. The machine ran at 9.0x real time. Share of the engine thread's time:

| part | share | what it is |
|---|---|---|
| present (VL_Present) | 29.8% | `_write_rows` turns the whole 320x200 PAL8 screen into the card's four planes every refresh, even when the native view draws from the list |
| calctics | 35.1% | RFL_CalcTics: mostly waiting on the machine's clock (SD_WaitTick), not drawing |
| capture list | 10.9% | `_capture_draw_list` (REND-01) |
| sprites | 10.3% | RFL_DrawSpriteList, the PAL8 sprite blits |
| updatetiles | 5.1% | the dirty tile blocks copied |
| dirty + draw func | 3.2% | |
| game logic, between refreshes | 3.5% | everything the game itself does |
| anim tiles, erasers | 2.3% | |

The game logic is about 4%. The cost is the pixel work in GDScript, and the largest single part of it is the card conversion, which nobody sees when the native view is on.

## Plan (Thursday)

1. **Native card conversion.** Move `_write_rows`'s PAL8-to-planes loop into native code, in the d2opl library (built for Windows, Android arm64/x86_64, Linux by tools/build_native.py). It must be byte-identical: keep the GDScript loop as the reference in a test (the tests/perf01_blits.gd pattern). Design question first: Godot's packed arrays are copy-on-write, so a native call cannot write into the card's plane arrays passed as arguments. Either the card's planes move into a native object that GDScript reads from, or the call returns one block that replaces the planes. Measure both.
2. **Skip what nobody sees, where it is safe.** Work out which screens read the card back (the status window's overlay, fades, menus, text, REND-01R's comparisons). Classic mode keeps the faithful card path unchanged.
3. **Then** sprites, tiles and the list capture, the same way, measured after each step.
4. **Measure on the phone** (USB debugging, logcat; the host logs underruns and dropped stalls). Add a speed check with a large margin so slowdown cannot return unseen.
5. Check whether the Android map tearing is still there once the phone keeps up.

The local model (tools/ask_local.py, qwen3.8:27b) can draft the C loops and their byte-identical tests from a task file. Review stays here.
