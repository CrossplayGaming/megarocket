## Pre-ledger boundary

Nothing in this folder is pre-ledger *code*: the Godot project does not exist yet. The folders
`keen13/`, `omnispeak/`, `omnispeak-ref/`, `refkeen/`, `keendreams/`, `keen6/`, `keen6patch/` are
reference material copied from Megarocket, not components. Their own harnesses (`keen13/verify`,
`keendreams/verify`) are read for cases and ideas; nothing they verified counts as verified here.

## Architecture commitments

Locked once feature work begins. These are the Duke Nukem II recreation's commitments, carried
over because they were what made that port provable, with the changes seven games and Android
require (A9, A10, A14, A15).

| # | Commitment | What it buys |
|---|---|---|
| A1 | Each simulation advances only in whole original frames, one call per frame, at a fixed rate chosen by the shell: the Vorticons engine's vblank-locked tic, Galaxy's and Dreams' 70 Hz tic clock with the originals' tic-count catch-up rule reproduced. | Replays, comparison against the original, speed independent of machine. |
| A2 | Simulation arithmetic is whole-number only, through explicit 8-bit, 16-bit and 32-bit helpers that wrap as Borland C did; Galaxy's 16.16 fixed point reproduced as integers. No decimals in any simulation. | No drift. Overflow behaves as in the original. |
| A3 | No simulation touches the engine. Each draws the way its original did, into one emulated EGA card (registers, four planes, latches, panning, palette, page flipping) shared by all three engines. The picture is read back from that card. The same drawing calls also emit a draw list (what image, where, in what order) for the modern renderer. | Headless runs; pictures identical by construction; one renderer for seven games; native resolution is a redraw of the list. |
| A4 | Player input enters each simulation as the original's own per-frame control structure. Galaxy and Dreams sessions are recorded in the originals' demo formats; Vorticons in a port-own format of the same shape. Menu and hot-key input is recorded alongside. | Every session is replayable; Galaxy/Dreams demo files written here play in the originals. |
| A5 | Randomness is each original's table and index, held in simulation state. | Identical random sequences. |
| A6 | A hash of the complete simulation state is available after any frame, for every engine. | Determinism checks name the frame where two runs part. |
| A7 | The complete simulation state — including the map planes and the card — can be stored and restored. | Round-trip tests; quicksave anywhere in all seven games. |
| A8 | No wall-clock time, frame time or display size inside a simulation, except the view width in tiles, which is the original's in Classic. Actor activation reads the view width (the user's widescreen decision) through one named function per engine. | Widescreen is one number and one function; parity is claimed at the original width. |
| A9 | Shell and games are separate. The shell owns window, settings, input mapping, touch overlay, audio output, drawing, file locations, game detection and import. Each engine is a module behind one interface; each game is that engine plus an episode table. | One launcher, one options system, one touch layer for seven games. |
| A10 | Each engine's code is one class built up over a few scripts, each extending the one before, in the reference source's order, every function carrying the reference's name. The reference for Keen 1–3 is the reconstruction; for Keen 4–6 omnispeak (upstream, not the Megarocket fork); for Dreams the released original source. | A reader can check any function against its reference line by line. |
| A11 | Blocking flows (waits for a key, a refresh, a sound's end) run as written, synchronously, against the machine's virtual clock: every wait advances the clock and delivers what fell due (timer interrupts, keys, refreshes). Headless runs need no threads; the real-time shell paces the waits from outside (an engine thread blocked at a wait). Snapshots are taken at frame boundaries, where the only stack is the level or map loop. | One-for-one control flow; no coroutine chains through the game code; determinism by construction. (Revised 2026-10-07 from "coroutines for blocking flows".) |
| A12 | Original game files are read at run time from storage the user supplies or the app imports into. Nothing derived from them is ever written into the repository or a build. omnispeak's own metadata files are engine-own and may be bundled. | The legal line. |
| A13 | Each engine's working memory is one block with the original's allocator; a pointer is an offset into it. | Reads past the end of one allocation land where they did in the original. **2026-10-08:** the Galaxy port did not follow this: structs and buffers are Godot objects and arrays, wrapping only where C wraps (its twelve demos match omnispeak regardless); see J-16. |
| A14 | The only native code is the OPL emulator (`d2opl`, GPL, carried from Duke), built for Windows, Linux and Android arm64/x86_64 from one CMake file. Everything else is GDScript, so the Android build is an export, not a port. | Android parity is structural, not a later effort. |
| A15 | Every added option is a shell setting, read by the shell, never by a simulation, except the widescreen activation width (A8). | The fidelity line is enforceable by grep. |
| A16 | **Controller-complete from the first screen (user, 2026-10-06).** Every function of the shell and of every game — every menu item, prompt, hot-key action, text field, cheat, option, save and load — is reachable and operable with a gamepad alone, and the path walker (HARN-09) proves it in pad-only mode. No screen-bearing unit is `verified` until that pass is in its evidence; a screen that needs a key the pad cannot produce is a failing check, not a note for later. Keyboard-only and touch-only get the same rule. | Megarocket retrofitted this late and never fully got there. Here it is a gate on every unit, not an audit at the end. |
| A17 | The port keeps the oracle's time to the refresh. The machine runs at DOSBox's speed: drawing is charged by the original routine's instruction count (DrawPage's 5 a tile and 56 a copied tile, DrawPic's 7 and its width a line, DrawSprite's rows, DrawTile, DrawChar) at a fixed 20000 instructions a millisecond, as DOSBox's normal core counts them; file work the port does at once is a named cost (`costs`, fitted with `tools/fit_costs.py` / `tools/fit_option.py`); the refresh period and the phase of the reprogrammed timer are fitted to the recordings (`dosbox_timing` on the engine). The picture is captured as DOSBox's beam draws it: the first visible line 37 scan lines after the retrace begins, then bands of 4 picture rows each when the beam reaches them (anything drawn on the visible page right after a retrace shows in that same refresh). `tools/timing_score.py` holds a run to the recording picture by picture and refresh by refresh; keys posted to DOSBox land unevenly and are fitted per recording at refresh resolution (`tools/fit_keys.py --timing --refreshes`). | Revised 2026-10-07: with these, Keen 1's 30 s and 50 s recordings match every picture's duration exactly. A uniform cost per video access was tried and is wrong (it disturbs the loading fits). |
| A18 | **Creative-suite readiness (user, 2026-10-09).** Every image and sound is reachable by a stable name with its metadata (size, frames, anchor, hit box, colours used); every engine's graphics and sounds pass through one load-time asset stage (where packs, restyles and Keen's colours apply, alike in Classic and Enhanced, by transforming the cached data, never the emulated card); every engine writes its levels as well as reads them; tiles are named by use (solid, slope and angle, pole, hazard, edge piece and its joins); a level can start anywhere with Keen set down there. The suite's own interface (menus, panels, font, game picker) is original art in EGA colours and reads no game file; every tool is per game and offers only the games the player owns, whose own files then supply the parts and the hosting characters (mascot, tutor), a version per game (user, 2026-10-09). | Keen Maker, Asset Studio and Keen's Closet (v1.5) build on v1.0 instead of reworking it, and work with any subset of the games. |

| HARN-20 | Frame lock. Each picture the port presents after a fade-in is held until the refresh at which the recording first shows it, counted from that fade-in; a picture the port would show later is never moved earlier, and the restart's load is left to the costs. It stands in for the original's processing time per frame, which the port does not model (the 70 Hz game clock drifts against the 70.086 Hz display, a 15.6 s beat, and where a tic falls within a frame's work of a retrace the original's picture misses it: the 3-then-1 clusters). With it, a death's restart reads the DOS clock a BIOS tick off in some sessions (the reload follows the last frame's work): those readings are fitted per restart as the clock at the start is (`seed_ticks` in the session's .port.json). The session scorer treats a restart as the opening again (its pictures in order, its durations summed to within 2 refreshes, the count restarting after its black). | REPLAY-G: the game's logic (objects, physics, random choices, input) through whole sessions, restarts included, independent of TIME-G's frame timing. | `python tools/galaxy_case.py <game> <case> --lock`; `python tools/fit_galaxy.py <game> <case> --start port --lock` | The original's frame timing itself (TIME-G); a picture the port shows late. |
| HARN-21 | Game-clock parity (Keen Dreams). drm_boot --tc_adds adds tics to TimeCount at a chosen moment. The frames accelerate and fall only on the clock's odd tics (AccelerateX, DoGravity), and a long load's first frame clamps the clock back to its last frame + MAXTICS (6, even), so the parity in play is the one carried through the loads. Where the original's slower loads (TIME-D) leave it a tic apart, one added tic before a load restores it (kdreams level01, posted keys). | REPLAY-D: a session whose motion differs by a fraction of a pixel from the first jump. | `python tools/fit_dreams.py <game> <case>` (tried before each load) | Superseded where TIME-D models the loads; kept for sessions it does not. |
| HARN-22 | Key feeder. It taps Enter through the start-up screens, then from the tick the BIOS video mode becomes 0Dh it feeds each make and break code of the case's timetable through the keyboard controller's D2h command, so the byte arrives as from the keyboard, through IRQ 1 and the game's own handler. ## Units

IDs are never renumbered. Where one check covers all seven games, the unit is one row with the
game named in the evidence; where behaviour differs per engine, there is a row per engine
(V = Vorticons 1–3, G = Galaxy 4–6, D = Dreams).
